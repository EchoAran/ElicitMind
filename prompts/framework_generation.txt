# DECOMPOSITION STEPS:
## Step 1: Analyze the initial requirements to extract core business goals, target user roles, business entities, and critical workflows.
## Step 2: Consult the Reference Dimensions to identify relevant but unstated requirement concerns (such as exceptions, external interfaces, performance thresholds, operational constraints, acceptance criteria) that are pertinent to this specific project. Proactively establish exploratory Sections and Topics for pertinent dimensions even if they were not explicitly mentioned in the initial brief.
## Step 3: Formulate project-tailored Sections (Section) representing high-level functional domains, lifecycle stages, or quality concerns:
  - Sequence sections in natural interview priority and logical flow, numbered sequentially as "section-1", "section-2", etc.
  - section_content: Clearly summarize the domain area or lifecycle dimension. Adapt, merge, and contextualize concerns to the target system rather than copying generic reference titles mechanically.
## Step 4: For each Section, formulate concrete Topics (Topic):
  - Focus each topic on a specific business scenario, feature capability, boundary rule, or key quality concern.
  - Number topics sequentially under their parent section matching "topic-X-Y" where X is the parent section index and Y is the topic index (for example, "topic-1-1", "topic-1-2").
  - topic_content: Clearly define the specific scenario, workflow, or technical concern to explore during the interview.
## Step 5: For each Topic, design specific Information Slots (Slot):
  - Slots represent concrete attributes, decision points, boundary conditions, or operational rules to elicit from the interviewee.
  - Number slots sequentially under their parent topic matching "slot-X-Y-Z" where X and Y match the parent topic indices and Z is the slot index (for example, "slot-1-1-1", "slot-1-1-2").
  - slot_key: Accurate and concise name of the requirement attribute or operational boundary. Name concrete business attributes of the target domain; never name generic requirements meta-concepts.
  - is_required: A boolean (true or false).
    - Set to true if the core scenario, primary workflow, or mandatory rule of this topic cannot be understood, executed, or verified without this information. Essential functional behavior, critical failure handling, or key operational constraints vital to this scenario must be marked required.
    - Set to false for supplementary exploratory slots, such as optional edge variations, secondary configuration details, or additional quality inquiries that enrich understanding but are not prerequisite to understanding the core scenario.
    - Topic Baseline Anchor (MANDATORY): Each topic MUST have at least one core required slot (is_required: true). Even when an exploratory topic addresses supplementary constraints or quality attributes, mark its primary defining attribute or foundational baseline slot as is_required: true!
    - Within each topic, order non-required slots by inquiry priority.

# STRICT RULES AND GUARDRAILS:
1. Grounding vs Elicitation Targets: Distinguish between established facts and elicitation inquiries. The initial requirements provided by the user are an initial entry point, not an exhaustive boundary. Dimensions not explicitly stated in the initial brief may be established as exploratory Sections, Topics, and Slots ONLY when genuinely pertinent to the specific project's operational environment and lifecycle; do NOT copy irrelevant dimensions mechanically as a checklist. Elicitation targets MUST NOT be asserted as already-confirmed facts or verified rules.
2. Structural Consistency: Maintain a clean 3-level hierarchy (Section -> Topic -> Slot). Sibling elements at the same hierarchy level must avoid duplicate or overlapping concerns. Focus on distinct business responsibilities rather than forcing artificial completeness against the reference catalog.
3. ID Formatting and Hierarchy Consistency: Use exact lowercase hyphenated numbering strictly ("section-X", "topic-X-Y", "slot-X-Y-Z"). Every topic must match its parent section prefix, and every slot must match its parent topic prefix. Each ID must be globally unique across the framework.
4. Pure JSON Array Output: Output ONLY a valid JSON array matching the format below. Do NOT output conversational filler, markdown explanations, or outer commentary.
5. Topic Required Anchor Slot: Every single topic MUST contain at least one required slot with "is_required": true. A topic is justified in the framework only if it defines a clear elicitation target; its core baseline attribute must be marked "is_required": true, while optional or edge variations can be "is_required": false. A topic where all slots are false is invalid and will be rejected as a contract violation.
