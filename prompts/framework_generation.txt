# DECOMPOSITION STEPS:
## Step 1: Requirements and Domain Baseline Analysis:
  - Analyze the initial user brief to identify core business objectives, key stakeholder roles, domain entities, and central workflows.

## Step 2: Multi-Dimensional Evaluation and Section Formulation:
  - Consult the Reference Dimensions to identify applicable functional, operational, technical, and quality concerns pertinent to this specific project.
  - Establish dedicated Sections for distinct concern areas that are relevant or exploratory for the target system (e.g., business data/interfaces, operational constraints, system protection, or delivery/validation). Avoid overly aggressive pruning or prematurely collapsing distinct concerns into an overly compressed set of generic sections.
  - Section-level pruning should be balanced: Omit a reference dimension only when it is genuinely inapplicable or irrelevant to the project domain. There is NO need to artificially force all 10 dimensions if certain dimensions have no meaningful role in the project.
  - Number Sections sequentially as "section-1", "section-2", etc., arranged in a logical interview flow from business purpose and functional scope to technical, operational, and delivery concerns.
  - section_content: Clearly articulate the domain area or lifecycle concern using domain-tailored language for the target system.

## Step 3: Topic Specialization:
  - For each Section, formulate concrete Topics representing distinct scenarios, capabilities, operational rules, or boundary investigations.
  - Number topics sequentially under their parent section matching "topic-X-Y" where X is the parent section index and Y is the topic index (for example, "topic-1-1", "topic-1-2").
  - Apply selective topic-level tailoring: Select and detail relevant subtopics that genuinely apply to the project's operational reality, omitting specific subtopics that have no bearing on the domain.
  - topic_content: Clearly define the specific scenario, workflow, or technical boundary to explore during the interview.

## Step 4: Slot Design and Required Baseline Anchors:
  - For each Topic, design specific Information Slots (Slot) representing concrete attributes, decision points, boundary conditions, or operational rules to elicit from the interviewee.
  - Number slots sequentially under their parent topic matching "slot-X-Y-Z" where X and Y match the parent topic indices and Z is the slot index (for example, "slot-1-1-1", "slot-1-1-2").
  - slot_key: Accurate and concise name of the requirement attribute or operational boundary. Name concrete business attributes of the target domain; never name generic requirements meta-concepts.
  - is_required: A boolean (true or false).
    - Set to true for the baseline attribute or core decision indispensable to defining that topic's scenario.
    - Set to false for supplementary exploratory slots, such as optional edge variations, secondary configuration details, or additional quality inquiries that enrich understanding.
    - Topic Baseline Anchor (MANDATORY): Every topic MUST contain at least one required slot (is_required: true) establishing its baseline definition. Even for exploratory or quality topics, designate its primary defining attribute as is_required: true!
    - Within each topic, order non-required slots by inquiry priority.

# STRICT RULES AND GUARDRAILS:
1. Balanced Structural Coverage: Provide thorough elicitation coverage across the project's pertinent requirements dimensions. Avoid overly aggressive section pruning or over-merging that collapses distinct business or technical areas into too few sections. Select and establish dedicated Sections for all dimensions that are meaningfully applicable or exploratory for the system, without forcing irrelevant dimensions artificially.
2. Domain Contextualization: Formulate every Section, Topic, and Slot using concrete domain terminology of the target system rather than copying generic catalog labels mechanically.
3. Clean 3-Level Hierarchy: Strictly maintain Section -> Topic -> Slot. Sibling elements at each level must represent distinct responsibilities without redundant overlapping.
4. ID Formatting and Hierarchy Consistency: Use exact lowercase hyphenated numbering strictly ("section-X", "topic-X-Y", "slot-X-Y-Z"). Every topic must match its parent section prefix, and every slot must match its parent topic prefix. Each ID must be globally unique across the framework.
5. Topic Required Anchor Slot: Every single topic MUST contain at least one required slot with "is_required": true. A topic is justified in the framework only if it defines a clear elicitation target with a mandatory core attribute; topics with all false slots violate the contract and will be rejected.
6. Pure JSON Array Output: Output ONLY a valid JSON array matching the format below. Do NOT output conversational filler, markdown explanations, or outer commentary.
